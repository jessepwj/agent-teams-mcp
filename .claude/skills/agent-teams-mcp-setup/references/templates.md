# 文件模板（team-mode MCP 版）

## 项目 CLAUDE.md **+** AGENTS.md（团队操作指南）

⚠️ **必须生成两份内容相同的文件**：

| 文件 | 谁读 | 何时读 |
|------|------|-------|
| `CLAUDE.md` | Claude Code（team-lead） + claude-code worker | 会话启动 / `/compact` 后 / worker 启动 |
| `AGENTS.md` | codex worker（默认全员 codex 都读这个） | worker 启动 |

两个文件**内容完全相同**——只是 codex CLI 和 Claude Code 找的文件名不一样。

**生成步骤**：先按下面模板写 `CLAUDE.md`，然后 `cp CLAUDE.md AGENTS.md`。

**任何后续修改两边一起改**。custodian 在合规 audit 时应检查 `diff CLAUDE.md AGENTS.md` 必须无输出，否则 codex worker 拿到的项目上下文会陈旧。

生成位置：**项目工作目录**（不是 `.plans/` 内）。

**动态生成**：仅包含 Step 2 确认的角色。下面示例是完整团队，删除不用的行。

```markdown
# <Project Name> - Team Operations Guide

> Auto-generated by agent-teams-mcp-setup. 按需修改。
> 这个文件让 team-lead 知识跨 context 压缩持久化。

## Team-Lead Control Plane

- team-lead = 主对话本身，不是 spawned worker
- team-lead 拥有用户对齐、scope 控制、任务拆解、phase 转换
- team-lead 维护项目全局事实：主 task_plan.md、decisions.md、本 CLAUDE.md
- team-lead 决策一个工作流改进是项目本地还是回写到 agent-teams-mcp-setup
- **不再 spawn 标准 subagent**：团队建好后所有工作都通过 worker。不要再用 standalone Agent/subagent（Explore、general-purpose）—— 会绕过团队 planning 文件和协调。唯一例外：永久加新 worker

## Task 派发协议（team-mode MCP 版）

### 派发渠道：双轨

team-mode MCP 没有跨 worker 共享的 task list（codex worker 没 TaskList 工具）。
任务通过两条线下发：

1. **文件事实源**：`.plans/<project>/<agent>/task_plan.md` —— lead 维护，详细任务清单
2. **触发消息**：`mcp__team-mode__send_message(team, text="@<agent> 你的新任务在 .plans/.../task-X/，请确认。")`

worker 收到 @ 通知后读文件，按文件干活。

> **lead 私人 todo 看板**：lead 自己用 `TaskCreate`/`TaskList`/`TaskUpdate` 当本会话待办没问题——纯 lead 私用。但**不能拿 TaskCreate 当跨 worker 派发渠道**（worker 看不到）。

### 大任务（特性、新模块）—— 发送前 STOP AND CHECK

**给 worker 派大任务前，验证消息含以下 6 项。少任意一项，加上再发。不要省 —— worker 依靠这些才能正确工作。**

1. **Scope**：建什么，影响哪些用户路径 / API / 文件范围
2. **Success criteria**：什么算完成，如何验证
3. **Non-goals**：明确不做什么，防止顺手扩 scope / 重构
4. **文档提醒**："请建 task 子目录 `<prefix>-<task-name>/` 含 task_plan.md + findings.md + progress.md，并在自己根 findings.md 加索引项"
5. **依赖**：依赖哪个 research/任务，关键文件路径行号
6. **Review 期望**：完成后是否需要 review，review 重点是什么

例：
```
mcp__team-mode__send_message(team="<project>", text=
  "@backend-dev 新任务：实现 auth 模块。
   Scope: JWT 登录 + refresh token + auth middleware。
   Success criteria: 登录/刷新/鉴权成功路径和错误路径有测试，API docs 同步。
   Non-goals: 不重写现有用户模型，不引入新认证框架，不改前端 UI。
   依赖：researcher 的 findings 在 .plans/<project>/researcher/research-auth/findings.md
   请建 task-auth/ 子目录并更新自己根 findings.md 索引。
   这是大特性，完成后 @reviewer 请审，重点看 token 过期处理和 doc-code sync。")
```

任务子目录前缀：
- backend-dev / frontend-dev: `task-<name>/`
- researcher: `research-<topic>/`
- e2e-tester: `test-<scope>/`
- reviewer: `review-<target>/`
- custodian: `audit-<scope>/`

### 小任务（bug、配置改）

直接消息描述。无需 task 子目录或 review。
```
mcp__team-mode__send_message(team="<project>", text="@frontend-dev 修登录表单 XSS，src/auth/login.tsx:42")
```

## 通讯快查

| 动作 | 命令 |
|------|------|
| 派任务给单个 worker | `mcp__team-mode__send_message(team, text="@<name> ...")` |
| 派任务给多 worker | `text="@<name1> @<name2> ..."`（必须每个都明确 @） |
| dev 找 reviewer | dev 在自己 reply 里写 `@reviewer ...`（lead 通过 lead-observability 同步看到） |
| 看活的 worker | `mcp__team-mode__worker_list(team="<project>")` |
| 复活死 worker | `mcp__team-mode__worker_add(team, name, on_existing="reuse")` |
| 软删 worker | `mcp__team-mode__worker_remove(team, name)`（profile 保留可复活） |
| 看 lead inbox（兜底） | `mcp__team-mode__inbox_read(team="<project>")` —— 通常不需要，Stop hook 自动推 |

## 状态自检

| 看什么 | 怎么看 |
|--------|-------|
| Worker 列表 | `mcp__team-mode__worker_list(team)` —— sessionState alive/dead |
| 团队列表 | `mcp__team-mode__team_list()` —— ownerStatus alive/orphan |
| 快速扫 | 并行读各 worker 的 progress.md |
| 深入 | 读 worker findings.md（索引）然后特定 task 子目录 |
| 方向校准 | Read `.plans/<project>/task_plan.md` |
| 恢复项目 | Read team-snapshot.md → 检查 staleness → 用缓存 prompt 调 worker_add(on_existing=reuse) → 读各 worker findings.md 索引 |

阅读顺序：**progress（在哪）→ findings（遇到什么）→ task_plan（目标是什么）**

## Review Dimensions

> 项目专属 review 维度。reviewer 每次 review 都给每个维度评分
> team-lead 在 setup 时按项目目标和用户质量优先级定义
> 推荐 3-5 个维度。标准 checklist（安全/质量/性能/doc-sync）总是叠加

| # | 维度 | Weight | STRONG 长这样 | WEAK 长这样 |
|---|------|--------|--------------|------------|
| RD-1 | (例：Product depth) | high | 处理真实用户会碰到的边界——空态、错误恢复、并发 | 仅 happy path；错误态显示 raw exception 或缺失 |
| RD-2 | (例：Code testability) | medium | 关键行为有集成测试覆盖，加新 case 容易 | 没测试，或测试耦合实现细节，重构就挂 |

(team-lead 在 Step 1 按项目类型和用户优先级填。删示例行换实际维度)

## Harness Checklist

team-lead 在 phase 边界 review（不是每个任务）：

### Operational Health（每个 phase 边界）

- **Docs harness**：Read CLAUDE.md + 主 task_plan.md —— 还准吗？陈旧 → 派下个 phase 前更
- **Observability harness**：Grep progress.md "error|fail" —— 失败有没有详细日志（尝试步骤、确切错误、根因）？
- **Invariant harness**：review Known Pitfalls —— 有没有该升为 reviewer checklist 项或自动测试断言的？
- **Replay harness**：这个 phase 产生了可复用模式（搜索策略、架构模板、test plan）吗？有 → 标 [TEAM-PROTOCOL] 备查

### Assumption Audit（模型升级或项目复盘）

> 每个 harness 组件编码了对模型局限的假设。
> 这些假设会过时。模型升级 / 项目复盘 / 某机制持续无价值时审

| 组件 | 编码的假设 | 还 load-bearing 吗？ | 行动 |
|-----|----------|--------------------|------|
| Task 子目录 | 模型不分解会失去连贯性 | 看：worker 用子目录有效吗，还是 overhead > value？ | 留 / 简化 / 移除 |
| 3-Strike 协议 | 模型无 guardrail 会无限重试 | 看：本 phase 实际触发几次？ | 留 / 提阈值 / 移除 |
| Context recovery 协议 | 模型 compact 后没显式状态重载就回不来 | 看：模型自然从文件接得上吗？ | 留 / 简化 / 移除 |
| 任务粒度 | 模型一次处理大 scope 不行 | 看：粗一点会损失质量吗？ | 留 / 加粗 |
| Reviewer 通过 | 模型自评不可靠 | 看：reviewer 抓了 dev 没的真问题，还是大多盖章？ | 留 / 减频率 / 简单任务跳过 |
| Review Dimensions 评分 | 通用 checklist 漏项目专属质量 | 看：维度评分驱动了超出标准检查的反馈吗？ | 留 / 调维度 / 移除 |
| CI gate before review | 模型不强制就跳验证 | 看：dev 自愿跑 CI 吗？ | 留 / 信任 dev |
| Doc-code sync 规则 | 模型代码改完忘更文档 | 看：doc drift 还是问题吗？ | 留 / 放宽 |

**决策规则**：组件上 phase 触发 <2 次 **且** 移除不会有可观察质量下降 → 候选移除/简化。决定记 `decisions.md`。

**原则**：有趣的 harness 组合不会随模型变强而缩水——它们移动。移除不再需要的，加新机制覆盖现在能做到的能力。

## Known Pitfalls

> 发现重复失败模式时 append。每条防止同样错误再发生。
> 格式：症状、根因、修复、预防。

(初始空 —— team-lead 从 3-Strike 解决、reviewer [BLOCK] 修复、任何重复失败添)

## Style Decisions

> 项目期间捕获的用户 taste 偏好。
> 同一模式出现 3+ 次时 custodian 应编码到 golden_rules.py。
> 格式：决策、来源（用户反馈/review/事件）、enforce 状态。

| # | 决策 | 来源 | 状态 |
|---|------|------|------|
| (例) SD-1 | 变量名 camelCase 不 snake_case | 用户反馈 Session 2 | Manual |

状态值：
- `Manual` —— 仅文档化，reviewer 按惯例查
- `Pending automation` —— 出现 3+ 次，等 custodian 编码
- `Automated (GR-N)` —— 编码进 golden_rules.py，机械强制

## Key Protocols

| 协议 | 触发 | 动作 |
|------|------|------|
| 需求对齐 | 团队建好、dev 开始前 | researcher 探代码库（T0a），然后 team-lead 与用户对齐（T0b）。更新 task_plan.md §1-§2 |
| Plan stress-test | 架构最终化前 | 派给 researcher："stress-test 这个 plan，走每个决策分支"。从 findings.md 读结论 |
| 3-Strike escalation | worker 报 3 次失败 | 读其 progress.md，给新方向或重派 |
| Code review | 大特性/模块完成 | dev 在 findings.md 写变更摘要，reply 里 @reviewer |
| Phase 推进 | phase 完成 | research 完：读 findings 更主 plan。dev 完：等 reviewer [OK]/[WARN] |
| Context overflow | worker 报 context 长 | 进度已存盘，恢复 worker 或 spawn 继任 |
| CI gate | 任何代码改动（dev 完任务） | 跑 CI 脚本，全 PASS 才送审。CI 挂 = 任务未完 |
| Guardrail capture | 3-Strike 解决，或 reviewer [BLOCK] 修完 | 问：会复发吗？是 → 加 Known Pitfalls；通用 → [TEAM-PROTOCOL] |
| Custodian audit | 2-3 个 dev 任务完后，或 phase 边界 | team-lead 触发 custodian 合规扫描；custodian 报 gap |
| Pattern → Automation | reviewer 标 [AUTOMATE] 重复模式 | team-lead 派给 custodian → 写 check 脚本 → 加 CI |
| Taste capture | 用户表达 style/命名/结构偏好 | 记 CLAUDE.md Style Decisions。3+ 次 → 标 `Pending automation`，派 custodian 编码 |
| Style → Automation | Style Decision 达 `Pending automation` | custodian 编码进 golden_rules.py，状态变 `Automated (GR-N)`。不可机械化 → 保 Manual + 注释 |
| Template sync | 发现可持久工作流改进 | 先改 agent-teams-mcp-setup 源文件，再同步项目文档 |
| 团队重建时机 | 模板改动到影响 worker 行为 | 优先 phase 边界，不是中途 |
| Escalation 判断（dev） | dev 碰到含糊/不可逆/scope 改动决策 | 必须先问 lead 列选项 + 推荐 |

### 任务派发：最小化信息丢失

worker 间消息会丢细节。每次任务派发**必须**自包含：
- 引用 findings/docs 文件路径（worker 读文件，不读你的摘要）
- 验收标准在消息里（worker 知道何时算完）

### 模板级 vs 项目本地改动

按这个分类：

- **项目本地**：仅本项目文档/工作流需要
- **模板级**：未来项目应继承，先改 agent-teams-mcp-setup

典型模板级改动：
- team-lead 责任
- 角色边界
- onboarding 协议
- CLAUDE.md 结构
- task/finding/progress 约定
- 重建时机规则
```

```markdown
## 3. Phases Overview

任务拆 **垂直切片**（tracer bullet），不是按技术层水平切。

### Phases

- Phase 0：需求对齐 —— researcher 探代码库，team-lead 与用户对齐
- Phase 1：研究 —— 深挖技术问题和架构选项
- Phase 2：核心开发 —— 垂直切片实现 + TDD
- Phase 3：集成测试 —— E2E 测关键用户流
- Phase 4：Review & Cleanup —— code review verdict + 死代码移除
```
